| 选项 | 说明 |

#### 问题2：平台边界——0922 BRD 末尾「开票通知单核对」是否纳入本期范围 `[Business]` `[已澄清]`

> 上下文：0922 BRD 在 MBPLAP 数据映射后有一段：「触发开票通知单时，我们需要按照这个发票号核对收货数量和价格，确认无异常再触发，后续进行 payment。」该段在 0927 梳理版中已删除。历史初版 PRD 边界为「平台产出 = DSS 导入模板文件；不含 DSS/SPM 侧任何动作」。需确认这段核对是否属于 Case 5 平台功能。

| 选项 | 说明 |
|------|------|
| A | 不纳入：维持历史边界，平台产出到 DSS 模板 + Portal 下载/SharePoint 归档为止；开票核对属 DSS/SPM 侧人工动作（推荐，与 0927 梳理版一致） |
| B | 纳入：平台需提供「按发票号核对收货数量与价格」的核对视图/校验功能 |
| C | 二期再说，本期仅记录为 Open Item |

**【答复】：** A — 不纳入，维持平台边界：产出 DSS 模板 + Portal 下载/SharePoint 归档为止（2026-09-29 用户确认）

**【状态】：** 已澄清

#### 问题3：MBPLAP 手动触发入口是否保留 `[Business]` `[已澄清]`

> 上下文：0922 BRD 明确「保留手动触发的入口，根据分单号或 Pre-alert creation 日期进行批量查询和筛选并重新提交后，会和下一次定时任务一起运行」，且 17:00 运行需「先剔除 12 点已经运行的分单号」。0927 梳理版仅保留「每天中午 12 点、下午 5 点定时触发」，删掉了手动入口与剔除逻辑。新版 demo 任务中心有「新建任务（手动创建）」和「批量重跑」能力。

| 选项 | 说明 |
|------|------|
| A | 保留全部：定时两窗 + 手动按分单号/Pre-alert 日期批量重提交（随下次定时运行）+ 17:00 剔除 12:00 已运行分单号（推荐，与 0922 BRD 全量版及 demo 能力一致） |
| B | 仅定时触发：不做手动入口（按 0927 梳理版字面） |
| C | 手动入口保留，但手动提交立即运行（不随下次定时） |

**【答复】：** A — 保留全部：定时两窗 + 手动批量重提交（随下次定时运行）+ 17:00 剔除 12:00 已运行分单号（2026-09-29 用户确认）

**【状态】：** 已澄清

### [Technical] 类问题

#### 问题4：X-entry 邮件接收方案——直接发公邮还是自动转发 `[Technical]` `[已澄清]`

> 上下文：0922 BRD 中业务自己提出疑问：未来会有奔驰公邮再自动 Forward 给平台公邮，但自动转发会使转发人变成业务本人邮箱，与监控条件「发件人后缀 @bjfcl.com」矛盾；BRD 备注「可以要求代理和 IMS 同事发送邮件时直接发给这个公邮」。0927 梳理版简化为「接收邮箱：Portal 公邮」。demo 中公邮为 asn@mb.cn，监控规则按发件人 `*@bjfcl.com` + 主题「快件签收单」。

| 选项 | 说明 |
|------|------|
| A | 代理/IMS 直接发送 Portal 公邮（asn@mb.cn），不做转发（推荐，监控条件最简单可靠，与 0927 梳理版一致） |
| B | 奔驰公邮自动转发，平台按「原发件人」解析（依赖邮件头 X-Original-From 等，实现复杂） |
| C | 两者兼容：规则同时匹配直接发送与转发场景（监控条件放宽为正文/附件特征） |

**【答复】：** A — 代理/IMS 直接发送 Portal 公邮 asn@mb.cn，不做转发（2026-09-29 用户确认）

**【状态】：** 已澄清
